Wrap-up: Working with RL (Design of Experiments)

Most RL project failures are not “wrong equation” failures — they are uncontrolled variance, weak baselines, and missing ablations.

Design before you train

  • Question: one sentence on the hypothesis (“X improves sample efficiency on Y”).
  • Factors: algorithm, seeds, env suite, hyperparameters you will sweep.
  • Metrics: final return, AUC of learning curve, wall-clock, env steps.
  • Budget: how many runs you can afford; prioritize seeds over shiny variants.

Baselines that matter

  1. Random policy / scripted heuristic.
  2. Canonical model-free baseline (PPO or SAC) with published defaults.
  3. Ablation of your contribution (remove one component).
  4. Optional: a recent paper’s numbers — only if envs/metrics match.

Statistics without self-deception

  • ≥5 seeds for main claims (10+ if cheap).
  • Plot mean ± shaded std/sem; never a single cherry-picked run.
  • Report IQM / median when outliers dominate (rliable-style).
  • Pre-register which comparisons are confirmatory vs exploratory.
AUC = Σt return(t)  →  rewards learning speed, not only the endpoint

Report / paper skeleton

  1. Problem & claim
  2. Related work (3–5 lines)
  3. Method (equations + one figure)
  4. Experimental setup (envs, budget, seeds)
  5. Results + ablations
  6. Limitations (be specific)

Term project checklist

Proposal (Weeks 8–9)

Topic, baseline, success metric, compute plan, risk list.

Presentation (Weeks 15–16)

8–12 slides: problem, method, curves, one surprising failure, next step.

Report (Weeks 17–18)

Repro appendix: command lines, hyperparameters, seeds, hardware.

Code release

README with install, one-click train, and expected runtime on a laptop GPU/CPU.

Self-regulated learning. In the final writing weeks, timebox experiments: morning — run jobs; afternoon — write what you already know; evening — one small figure. Never write only after “all experiments finish.”
